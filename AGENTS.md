# AGENTS.md

Coffee Time: a Portuguese-language site where subscribers send the owner a short audio or video message for his vlogs, plus an owner panel and an MCP endpoint for his AI editor. Everything in the repo is in English; everything the user sees is in Portuguese.

Read first: [ARCHITECTURE.md](ARCHITECTURE.md), [docs/PRD.md](docs/PRD.md), [the flows](ARCHITECTURE.md#flows), [docs/design/](docs/design/).

## Stay inside ARCHITECTURE.md
Stay inside ARCHITECTURE.md. A feature that needs a service or pattern not listed there: stop, open an issue labeled `needs-owner` explaining why, and don't build it.

## Follow the design
Follow docs/design/ and the brand tokens. A new screen that changes the app's look (new layout, new navigation): stop, open an issue labeled `needs-owner` asking for a mockup. Small features that reuse existing patterns go straight to code.

Copy: short, correct Portuguese; icons, never emojis.

## Diagrams
Every map is generated, never drawn by hand: `docs/architecture/draw.py` (architecture map), `draw_flows.py` (one map per flow, numbered arrows) and `docs/assets/build.py` (README banner and high-level design). After changing one, run `docs/architecture/render.sh`, open every PNG, and fix anything that overlaps or crosses before committing. A new service or flow updates the map, the flow maps and `ARCHITECTURE.md` in the same PR.

## Verify a change
`npm run verify` runs the Worker locally on a free port with an isolated, throwaway D1 and fake data (`scripts/demo-seed.sql`). It checks the API, the MCP tools, the auth rules and the screens, and writes screenshots, a GIF and `verify-out/report.json` (`verdict: PASS|FAIL`). It never touches production and works offline. `npm run verify -- --keep` leaves the server running.

- **Builder** (Claude): makes the change, adds a check for it in `scripts/verify.mjs`, runs verify until PASS, looks at the screenshots, opens the PR.
- **Verifier** (Codex): runs verify on the PR head and reviews the diff against this file, ARCHITECTURE.md and docs/design/.

Never weaken an `auth:` check. A change that needs one changed stops and opens a `needs-owner` issue.

# Pipeline (issue → PR → verify → merge → deploy → health)

1. Work is queued as GitHub issues labeled `agent`, each with "Done when…". One open PR per repo at a time; an open `deploy-failed` issue goes first, even with a PR open.
2. Builder (Claude, cloud routine) claims the oldest `agent` issue (`in-progress` + a claim comment), works on `agent/<n>-<slug>`, runs `npm run verify`, opens a PR with the template (Summary, Cover, Decisions, Attention) and `Closes #N`.
3. CI runs typecheck, gitleaks, the deploy checks (dry-run bundle, bindings provision can create, additive migrations only), verify, and **main's `auth:` checks against the PR**, then posts the proof comment. Codex verifies: verify PASS **and** every "Done when" item has a check.
4. `auto-merge.yml` merges on Codex PASS for the head commit + green CI, then deploys. No human review: security is guarded by the `auth:` checks, and the merge script always runs from `main`. Two kinds of PR wait for the owner's `/approve` comment: changes to `.github/workflows/`, and removed/rewritten `auth:` checks. Fork PRs are held. Other sensitive paths (`wrangler*.jsonc`, auth code, `SECURITY.md`, `migrations/`) are only flagged 🔒. `circuit-breaker` stops a PR when the same Codex finding comes back after a fix, or after 5 failed rounds. A failed merge (conflict) is commented on the PR for the builder.
5. Deploy: provision → D1 bookmark (run summary) → migrate → deploy → production `GET /api/health?deep=1` → automatic rollback if it fails → issue `deploy-failed` (+`agent` for the builder, or +`needs-owner` for credential failures). Auto-merge holds every other PR until main deploys green.
6. Watchdog (hourly): frees claims with no PR after 3 h, re-asks Codex after 2 h of silence, mentions the owner on drafts, breakers and PRs stuck 12 h, and checks production health between deploys.
   **Production first:** a new binding in wrangler.jsonc (queue, bucket) needs nothing by hand: `scripts/provision.mjs` creates it on deploy, and CI fails a binding type it can't create. A new secret goes into `REQUIRED_SECRETS` in `src/index.ts`, so the deep health reports it if production lacks it.
7. Migrations are additive (expand now, contract in a later PR): old code keeps running during the deploy and after a rollback.
8. On merge, a GitHub Release `pr-N` (Summary, Decisions, proof GIF + screenshots) and a `CHANGELOG.md` line. Write the Summary for the owner.
   **Cover:** every PR names in `## Cover` one screenshot from `verify-out/` that best shows *this* PR's feature. If none does, add one to `scripts/verify.mjs`.
